To dwie zupełnie różne role, przypadkiem operujące na tej samej wartości:


onFulfilled / onRejected - Czyje to - callback użytkownika, przekazany do .then(fn)

resolve / reject - Czyje to - funkcje sterujące promise'a, stworzone przez konstruktor


onFulfilled / onRejected - Co robi - konsumuje wartość — dostaje ją i coś z nią robi

resolve / reject - Co robi - ustawia wartość — przełącza promise w stan settled


onFulfilled / onRejected - Kierunek - wartość wchodzi do niego

resolve / reject - Kierunek - wartość wychodzi z niego do promise'a


onFulfilled / onRejected - Kto woła - wrapper, w mikrotasku

resolve / reject - Kto woła - executor albo wrapper


onFulfilled to „co user chce zrobić z wynikiem". resolve to „przełącznik, który rozstrzyga promise'a". Nigdy nie są tym samym obiektem.

Handler jest mostem między dwoma promise'ami: czyta wartość z poprzedniego, a wynik wpycha do następnego.

type Handler = {
  onFulfilled: OnFulfilled<any, any> | undefined;
  onRejected: OnRejected<any> | undefined;
  resolveNext: (value: any) => void;
  rejectNext: (reason: any) => void;
}; 

Dopisane do resolve i reject "next" aby było jasne że będziemy się zajmować kolejną promise

To nie są metody, tylko pola trzymające referencje do funkcji. Handler to zwykły rekord danych, nie klasa z zachowaniem. Różnica jest istotna: nic tu nie ma this.

type OnFulfilled<T, R> = (value: T) => R;
type OnRejected<R> = (reason: any) => R;

3. Po co to w ogóle robimy

Dwa powody, oba o reentrancji — o tym, że handler wykonywany w pętli może dołożyć nowy handler do this.handlers:

a) Żeby nie zjeść nowego handlera. Gdybyś iterował po this.handlers i wyczyścił ją po pętli, wyrzuciłbyś handler dodany w trakcie — nigdy by się nie wykonał.

b) Żeby nie odpalić starego handlera dwa razy. Gdybyś nie czyścił wcale, kolejne wywołanie flushHandlers (a jest wołany i z settle, i z then) przeleciałoby po tych samych handlerach ponownie. To złamanie kontraktu Promise: handler odpala się dokładnie raz.

Jak forEach traktuje długość

Spec (Array.prototype.forEach) mówi: len jest odczytywane raz, przed pierwszym wywołaniem callbacka. Potem pętla leci while k < len, gdzie len to zamrożona liczba.

Konsekwencje:

Element dodany w trakcie → poza len → nie zostanie odwiedzony
Element usunięty przed odwiedzeniem → pominięty (jest sprawdzenie HasProperty, więc nie dostaniesz undefined)
Element nadpisany w trakcie → callback dostanie nową wartość, bo odczyt arr[k] dzieje się dopiero w momencie odwiedzenia

Czyli: zamrożona jest długość, nie zawartość.

Konstrukcja	Czy zobaczy dorzucony element
forEach / map / filter / some / every	nie — len czytany raz

for (let i = 0; i < arr.length; i++)	tak — arr.length re-ewaluowane co obrót → przy ciągłym push nieskończona pętla

for...of	tak — iterator sprawdza index >= length co krok → przy ciągłym push nieskończona pętla

for (let i = 0, len = arr.length; i < len; i++)	nie — ręcznie to samo, co robi forEach

a tutaj wnętrze bar jest przekazywane do tej promise którą zwraca bar() jako executor?

Nie. To jest dobre pytanie i warto mieć na nie precyzyjną odpowiedź, bo brzmi podobnie, a mechanizm jest inny.

Co robi silnik przy wywołaniu funkcji async:

Najpierw tworzy promise — pusty, pending. Zatrzymuje sobie na boku jego resolve i reject (spec nazywa to promise capability).
Potem zaczyna wykonywać ciało, synchronicznie, na bieżącym stosie — aż do pierwszego await, return albo throw.
Gdy ciało zwróci → silnik woła zapamiętany resolve. Gdy rzuci → reject.

Ciało nie jest nigdzie przekazywane. Nie ma tu wywołania funkcji z argumentami (resolve, reject). Ciało to jest ciało funkcji, a resolve/reject silnik trzyma poza zasięgiem Twojego kodu.
